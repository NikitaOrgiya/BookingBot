# BookingBot — Telegram-сервис онлайн-записи

## 1. Задача бизнеса

Небольшой сервисный бизнес (салон, мастер, консультант) обычно ведёт запись
вручную:

- клиенты записываются через переписку в мессенджере — администратор
  тратит время на согласование даты и времени вместо основной работы;
- ручное согласование не защищено от двойного бронирования одного и того
  же времени, если два клиента пишут почти одновременно;
- клиенты забывают о визите, если никто не присылает напоминание заранее;
- нет единого места, где администратор видит все записи, услуги и
  расписание — информация разбросана по переписке и памяти.

## 2. Решение

BookingBot — готовый сервис онлайн-записи поверх Telegram:

- Telegram-бот для клиента — запись без звонков и переписки, 24/7;
- автоматический пошаговый выбор услуги, даты и времени;
- атомарное бронирование на уровне базы данных — исключает двойную запись
  даже при одновременных попытках занять один слот;
- личный список записей клиента и самостоятельная отмена;
- административная панель — услуги, расписание, разовые блокировки,
  записи, настройки организации;
- автоматические Telegram-напоминания клиенту (за 24 часа и за 2 часа до
  визита);
- защищённая production-инфраструктура: авторизация, минимальные права
  доступа к данным, защищённые webhook и cron-эндпоинты.

## 3. Основные функции

### Для клиента

- запись через Telegram в любое время, без звонков;
- выбор услуги, свободной даты и времени в реальном расписании бизнеса;
- экран подтверждения перед созданием записи;
- просмотр своих будущих записей;
- самостоятельная отмена записи с учётом срока, после которого отмена
  недоступна.

### Для администратора

- защищённая веб-панель (вход по email и паролю, без публичной
  регистрации);
- dashboard с ключевыми показателями дня и недели;
- управление каталогом услуг (создание, изменение, деактивация);
- недельное расписание работы и разовые блокировки времени (отпуск,
  особые дни);
- список записей с фильтрами, сменой статуса (подтверждена / завершена /
  отменена / не пришёл);
- настройки организации: название, часовой пояс, горизонт бронирования,
  сроки уведомления и отмены, напоминания.

### Автоматизация

- атомарный расчёт свободных слотов с учётом расписания, блокировок и уже
  существующих записей;
- автоматические напоминания клиенту за 24 часа и за 2 часа до визита;
- регулярный фоновый процесс (cron), который сам находит и отправляет
  назревшие напоминания без участия администратора;
- повторные попытки отправки при временных сбоях Telegram API.

### Безопасность и надёжность

- разделение прав доступа на уровне базы данных: клиентский Telegram-бот,
  административная панель и фоновые задачи используют разные,
  минимально необходимые полномочия;
- защита от двойного бронирования на уровне самой базы данных, а не
  только в коде приложения;
- защищённые входные точки (Telegram webhook, cron-эндпоинт) —
  константная по времени проверка секрета, отказ по умолчанию при
  отсутствии настройки;
- идемпотентная обработка повторных внешних вызовов (Telegram может
  повторно прислать одно и то же обновление, cron может сработать более
  одного раза) — без двойных действий и без потери данных.

## 4. Технологический стек

- Next.js (App Router) + React + TypeScript (strict)
- Supabase: PostgreSQL, Auth, Row Level Security
- Supabase Cron: `pg_cron`, `pg_net`
- Telegram Bot API (grammY)
- Vercel (хостинг, production deployment)
- Vitest — unit- и интеграционные тесты
- pgTAP — тесты безопасности и корректности схемы базы данных
- Playwright — end-to-end тесты административной панели
- GitHub Actions — обязательный CI на каждое изменение

## 5. Архитектура

Клиентский сценарий:

```
Telegram client
  → Telegram webhook
    → Next.js server
      → booking domain (доступность, атомарное бронирование, отмена)
        → PostgreSQL / Supabase
```

Напоминания:

```
Supabase Cron (каждые 5 минут)
  → защищённый cron-эндпоинт
    → атомарный захват "созревших" напоминаний
      → Telegram Bot API
        → журнал доставки (успех / ошибка / пропущено)
```

## 6. Сложные технические задачи

- **Двойное бронирование.** Проверка свободного времени перед показом
  кнопки клиенту недостаточна: между показом и нажатием кнопки другой
  клиент может успеть занять то же время. Окончательное решение всегда
  принимает сама база данных в момент записи — параллельная попытка
  занять то же время физически не может пройти.
- **Одновременная попытка занять один и тот же слот.** Проверено не
  только в теории, но и настоящей параллельной нагрузкой: два независимых
  подключения одновременно пытаются занять одно и то же время — ровно
  одно успевает, второе получает понятный отказ "время уже занято", а не
  невнятную техническую ошибку.
- **Атомарная работа с базой.** Каждое бронирование, отмена и изменение
  статуса — единая, неделимая операция: либо применяется целиком, либо не
  применяется вовсе, без промежуточных "наполовину сохранённых" состояний.
- **Минимальные права доступа.** Каждая часть системы (клиентский бот,
  административная панель, фоновые задачи) имеет доступ ровно к тем
  данным и действиям, которые ей реально нужны — компрометация одной
  части не даёт доступа к остальным.
- **Защита входных точек.** И Telegram-webhook, и cron-эндпоинт
  напоминаний проверяют секретный ключ constant-time сравнением (без
  утечки времени ответа как способа подбора) и по умолчанию отказывают в
  доступе, если секрет не настроен, а не пропускают запрос.
- **Идемпотентная обработка Telegram-обновлений.** Telegram может
  повторно прислать одно и то же событие, если не получил вовремя
  подтверждение. Система переживает это без повторного выполнения
  действия и без "потерянных" сообщений — даже если процесс аварийно
  прерван прямо посреди обработки.
- **Защита от повторной отправки напоминаний.** Регулярный фоновый
  процесс может в теории сработать чаще, чем нужно, или дважды подряд.
  Механизм атомарного "захвата" задачи гарантирует, что два параллельных
  запуска не отправят одно и то же напоминание дважды.
- **Повторные попытки при временных ошибках.** Если Telegram временно
  недоступен, напоминание не теряется — система автоматически повторяет
  попытку с нарастающей паузой, но останавливается сразу, если ошибка
  окончательная (например, клиент заблокировал бота).
- **Восстановление зависших задач.** Если фоновый процесс аварийно
  прервётся в момент обработки конкретного напоминания, эта задача не
  "зависает" навсегда — по истечении разумного времени она автоматически
  подхватывается заново.
- **Часовой пояс бизнеса.** Все даты и время, которые видит клиент,
  считаются в часовом поясе конкретного бизнеса, а не сервера — включая
  корректную обработку перевода часов (переход на летнее/зимнее время).

## 8. Результат

- проект развёрнут в production и полностью работает;
- Telegram-бот принимает записи от клиентов;
- административная панель управляет услугами, расписанием и записями;
- автоматические напоминания реально доставляются клиентам в Telegram;
- фоновый процесс напоминаний запускается автоматически каждые 5 минут;
- проект готов к адаптации под конкретный бизнес: салон, отдельного
  мастера, консультации или другой сервисный формат с записью по времени.

## 9. Что можно адаптировать под клиента

- бренд и название;
- каталог услуг и их описание;
- цены;
- расписание работы;
- интервалы между слотами записи;
- горизонт бронирования (на сколько дней вперёд можно записаться);
- тексты сообщений бота;
- адрес и контактные данные;
- настройки напоминаний (за сколько времени и какие типы присылать);
- статусную модель записи под специфику бизнеса;
- дополнительные роли доступа в административной панели.

## 10. Ограничения текущей версии

Честно, без преувеличения:

- рассчитан на один бизнес с одной конфигурацией — не мультиарендное
  решение "из коробки" для нескольких независимых организаций одновременно;
- нет нескольких сотрудников с индивидуальными, независимыми друг от
  друга календарями внутри одного бизнеса;
- нет встроенной онлайн-оплаты;
- нет интеграции с внешними календарями (например, Google Calendar);
- между PostgreSQL и внешним Telegram API математически не гарантируется
  доставка ровно один раз в исключительно редком сценарии обрыва связи в
  самый момент подтверждения отправки — в этом (крайне маловероятном)
  случае клиент теоретически может получить одно и то же напоминание
  дважды; сама запись в базе данных при этом не дублируется и не
  теряется.

## 11. Варианты коммерческого развития

- базовая установка готового шаблона под новый бизнес;
- индивидуальная адаптация: бренд, услуги, тексты, расписание;
- поддержка нескольких специалистов с раздельными календарями;
- работа с несколькими филиалами;
- интеграция онлайн-оплаты;
- аналитика и отчётность для владельца бизнеса;
- интеграция с внешним календарём.
